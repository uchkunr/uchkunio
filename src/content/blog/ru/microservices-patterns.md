В монолите вызов функции возвращает либо результат, либо ошибку. В микросервисах он идёт через сеть, и появляются новые сценарии: ответ задерживается или теряется, операция выполняется дважды или остаётся неизвестным, выполнилась ли она. Каждый из паттернов ниже отвечает на один из этих сценариев:

| Паттерн | Какую проблему решает |
| --- | --- |
| Database per Service | Сервисы оказываются привязаны к таблицам друг друга |
| API Gateway | Клиент вынужден знать адреса десятков сервисов |
| Saga | Для операции, затрагивающей несколько сервисов, нет общей транзакции |
| Outbox и идемпотентный потребитель | Сообщение теряется или приходит дважды |
| Circuit Breaker | Неработающий сервис роняет и тех, кто его вызывает |
| Retry, backoff и jitter | Временные сбои и волна одновременных повторных попыток |
| Distributed Tracing | Запрос проходит через десяток сервисов, и непонятно, где возникла ошибка |

![Клиент, API gateway и три сервиса, у каждого своя база, события уходят в Kafka через outbox](/sketches/microservices/map.svg)

## Database per Service

Каждый сервис становится единственным владельцем своих данных, а остальные обращаются к ним только через API или события. Изменение одного столбца в общей таблице ломает сразу несколько сервисов, и независимый деплой теряет смысл. Даже внутри одного Postgres это можно обеспечить правами: после `CREATE SCHEMA orders AUTHORIZATION orders_svc;` другие роли не смогут обратиться к этой схеме без разрешения.

## API Gateway

Клиент обращается к одному адресу, а gateway направляет запрос нужному сервису и в одном месте выполняет аутентификацию и rate limiting. Бизнес-логика попадать в gateway не должна, иначе он постепенно превратится в новый монолит.

## Saga

Если заказ, оплата и склад живут в трёх разных сервисах, обернуть их в одну транзакцию не получится. Saga привязывает к каждому шагу компенсирующее действие, которое его отменяет, и при ошибке откатывает выполненные шаги в обратном порядке:

```ts
type Step = { name: string; run: () => Promise<void>; undo: () => Promise<void> };

async function runSaga(steps: Step[]): Promise<void> {
  const done: Step[] = [];
  for (const step of steps) {
    try {
      await step.run();
      done.push(step);
    } catch (error) {
      console.log(`${step.name} failed: ${(error as Error).message}`);
      for (const completed of done.reverse()) await completed.undo();
      throw error;
    }
  }
}
```

```text
order created
payment charged
stock failed: out of stock
payment refunded
order cancelled
```

Это оркестрация: шагами управляет единый центр. Альтернативный подход называется хореографией, и в нём сервисы сами реагируют на события друг друга. С ростом числа шагов оркестрацию проще отслеживать и понимать.

## Outbox и идемпотентный потребитель

Запись в базу и отправка сообщения в брокер не помещаются в одну транзакцию, поэтому сообщение записывается в таблицу outbox в той же базе, а доставку выполняет relay. Relay доставляет сообщение как минимум один раз, а значит, потребитель должен сам распознавать дубликаты. Оба паттерна вместе с реальными результатами разобраны в [отдельной статье](/ru/blog/transactional-outbox-pattern).

## Circuit Breaker

Если платёжный сервис перестал работать, продолжать слать ему запросы вредно обеим сторонам: вызывающий каждый раз ждёт таймаута, а восстанавливающийся сервис оказывается под новой нагрузкой. После серии ошибок подряд circuit breaker «открывается» и сразу отклоняет запросы, а через заданное время пропускает один пробный запрос:

```ts
async call<T>(fn: () => Promise<T>): Promise<T> {
  if (this.state === "open") {
    if (Date.now() - this.openedAt < this.resetMs) throw new Error("circuit open");
    this.state = "half-open";
  }
  try {
    const result = await fn();
    this.state = "closed";
    this.failures = 0;
    return result;
  } catch (error) {
    this.failures++;
    if (this.state === "half-open" || this.failures >= this.threshold) {
      this.state = "open";
      this.openedAt = Date.now();
    }
    throw error;
  }
}
```

Платёжный сервис не работает первые 1.5 секунды, порог составляет 3 ошибки, а время в открытом состоянии равно 1 секунде:

```text
   0 ms  closed -> payments 503   (closed)
 271 ms  closed -> payments 503   (closed)
 542 ms  closed -> payments 503   (open)
 812 ms  open   -> circuit open   (open)
1316 ms  open   -> circuit open   (open)
1566 ms  open   -> ok             (closed)
```

![Состояния circuit breaker: закрыт до 3 ошибок, открыт 1 с, затем решает одна пробная попытка](/sketches/microservices/breaker.svg)

В открытом состоянии запросы вообще не уходят в сеть. Пробный запрос на 1566-й миллисекунде проходит успешно, и breaker закрывается.

## Retry, backoff и jitter

Временную ошибку решает повторная попытка, но при двух условиях. Во-первых, у каждого сетевого вызова должен быть таймаут: `fetch(url, { signal: AbortSignal.timeout(2000) })`. Во-вторых, время ожидания с каждой попыткой удваивается и выбирается случайно:

```ts
const backoff = (attempt: number, baseMs = 100, capMs = 5000) =>
  Math.random() * Math.min(capMs, baseMs * 2 ** attempt);
```

Зачем нужна случайность, становится видно, когда сервис падает, а потом восстанавливается: все клиенты одновременно получают ошибку и одновременно повторяют попытку. Возьмём 1000 клиентов и четвёртую попытку:

```text
запросов в одном и том же окне 100 ms:  без jitter 1000,  с jitter 74
```

![1000 клиентов повторяют запрос: без jitter все сразу, с полным jitter запросы распределены на 0-1600 мс](/sketches/microservices/jitter.svg)

Повторять можно только идемпотентные операции. Чтобы платёж можно было отправить повторно, запрос приходит с idempotency key, и сервер выполняет его только один раз.

## Distributed Tracing

Один пользовательский запрос проходит через gateway и сервисы заказов, оплаты и склада. Каждый сервис передаёт следующему заголовок `traceparent` по стандарту W3C, и логи объединяются вокруг одного `trace-id`:

```text
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
               |  trace-id (весь запрос)           span-id (этот шаг)
```

Для HTTP-клиентов и серверов OpenTelemetry передаёт этот заголовок автоматически. Без него поиск ошибки в десяти сервисах превращается в ручное сопоставление десяти разных логов по времени.

У каждого паттерна своя цена: код, инфраструктура и сложность. Добавляйте его, когда проблема действительно появилась, а не заранее.
