[YardLens](https://github.com/uchkunr/yardlens) находит в потоке с камеры транспорт и людей, отслеживает их и считает тех, кто пересёк заданную линию. Объекты детектирует YOLO и сопровождает ByteTrack, а результаты в реальном времени передаются в веб-панель. Ниже собраны самые важные решения в проекте и причины, по которым они приняты.

## Очередь накапливает задержку

Допустим, камера выдаёт 25 кадров в секунду, а модель на процессоре успевает обработать лишь 5 из них. Если ставить в очередь каждый кадр, необработанных кадров будет становиться всё больше:

```python
camera_fps, model_fps = 25, 5
for minutes in (1, 10, 60):
    backlog = (camera_fps - model_fps) * minutes * 60  # кадры, ожидающие в очереди
    print(f"Через {minutes:>2} мин задержка: {backlog / model_fps / 60:.0f} мин")
```

```text
Через  1 мин задержка: 4 мин
Через 10 мин задержка: 40 мин
Через 60 мин задержка: 240 мин
```

![С очередью задержка растёт каждую секунду, с одним последним кадром она не превышает одного кадра](/sketches/yardlens/queue-vs-latest.svg)

Через час система будет выдавать за происходящее сейчас события четырёхчасовой давности. Поэтому в YardLens очереди кадров нет вообще: поток, читающий камеру, хранит только последний кадр, и каждый новый кадр занимает место предыдущего.

```python
with self._frame_ready:
    self._latest_frame = frame
    self._frame_seq += 1
    self._frame_ready.notify_all()
```

Проснувшись, поток анализа берёт не следующий кадр по очереди, а самый свежий. Кадры, которые модель не успела обработать, отбрасываются, и задержка не превышает одного кадра:

```python
with self._frame_ready:
    while self._frame_seq == last_seq and not self._stop.is_set():
        self._frame_ready.wait(timeout=1.0)
    frame = self._latest_frame
    last_seq = self._frame_seq
```

![Для каждой камеры: поток захвата хранит только последний кадр, инференс на 3 fps и отрисовка на 15 fps читают его независимо](/sketches/yardlens/threads.svg)

## Анализ и отображение работают с разной частотой

У каждой камеры три потока: чтение, анализ и отображение. Анализ выполняется 3 раза в секунду, а живая картинка обновляется 15 раз. Чтобы между двумя анализами рамка не застывала на месте, поток отображения сдвигает её вперёд по сглаженной скорости объекта:

```python
elapsed = min(max(timestamp - motion.seen_at, 0.0), self._max_extrapolation)
box = (
    motion.box[0] + motion.velocity[0] * elapsed,
    motion.box[1] + motion.velocity[1] * elapsed,
    motion.box[2] + motion.velocity[2] * elapsed,
    motion.box[3] + motion.velocity[3] * elapsed,
)
```

Предсказание ограничено величиной `max(1.5 / fps, 0.3)` секунды, то есть при 3 анализах в секунду оно не превышает половины секунды. Благодаря этому картинка остаётся плавной даже на медленном процессоре. А на снимках событий рисуется только настоящий результат модели, и предсказанные рамки туда не попадают.

## Одна модель, одна блокировка

Модель Ultralytics не рассчитана на несколько одновременных вызовов `predict`. Загрузка отдельной модели для каждой камеры умножила бы расход памяти на число камер, поэтому все потоки пользуются одной моделью по очереди:

```python
with self._lock:
    model = self._model
    # ...
    results = model.predict(frame, conf=confidence, classes=class_ids, device=self._device, verbose=False)
```

Платить за это приходится пропускной способностью: nano-модель на процессоре тянет несколько камер с частотой 2-5 кадров в секунду, а для большего нужен GPU.

## Потоки ничего не знают о базе

Потоки камер не знают ни об asyncio, ни о базе данных. Они лишь передают событие в event loop:

```python
def on_event(self, event: WorkerEvent) -> None:
    self._loop.call_soon_threadsafe(self._on_event, event)
```

Там события собираются в пачки по 100 штук или за 250 миллисекунд и записываются в базу одной транзакцией. Очередь ограничена 10 000 событий: если база отстала настолько, лучше отбросить событие с предупреждением, чем останавливать камеру.

```python
self._queue: asyncio.Queue[WorkerEvent] = asyncio.Queue(maxsize=10_000)

def submit(self, event: WorkerEvent) -> None:
    try:
        self._queue.put_nowait(event)
    except asyncio.QueueFull:
        logger.warning("Event queue full; dropping event", extra={"type": event.type.value})
```

## Браузер тоже ставит ограничения

По HTTP/1.1 браузер открывает к одному хосту не больше шести соединений, а каждый MJPEG-поток постоянно занимает одно из них. Если показывать на странице восемь камер в живом режиме, остальные запросы зависнут в очереди. Поэтому поток одновременно получают только четыре плитки, а остальные раз в секунду обновляют снимок:

```ts
const MAX_STREAMS = 4;

granted(key: string) {
  const index = this.holders.indexOf(key);
  return index >= 0 && index < MAX_STREAMS;
}
```
