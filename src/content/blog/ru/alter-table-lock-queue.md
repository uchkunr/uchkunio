Начиная с Postgres 11, `ALTER TABLE orders ADD COLUMN note text` выполняется мгновенно: таблица не переписывается, меняется только системный каталог. И всё же именно эта команда может на несколько секунд остановить продакшен. Причина не в самой команде, а в блокировке, которую она ждёт.

## Очередь блокировок

Каждый запрос берёт блокировку на таблицу. `SELECT` берёт самую лёгкую, `AccessShareLock`, и спокойно уживается с другими `SELECT`. `ALTER TABLE` требует `AccessExclusiveLock`, которая несовместима ни с какой другой блокировкой. Решающая деталь в том, что в Postgres блокировки выдаются в порядке очереди: запрос, пришедший позже, не обходит тяжёлую блокировку, которая уже стоит в очереди.

Проверим это на трёх сессиях. A читает таблицу внутри долгой транзакции, B добавляет столбец, а C отправляет обычный `SELECT`:

```sql
-- A: транзакция остаётся открытой 6 секунд
BEGIN; SELECT count(*) FROM orders;
-- B: через секунду
ALTER TABLE orders ADD COLUMN note text;
-- C: ещё через секунду
SELECT count(*) FROM orders;
```

```text
 pid | query                           | wait    | blocked_by
-----+---------------------------------+---------+------------
 116 | BEGIN; SELECT count(*) FROM ... | Timeout | {}
 123 | ALTER TABLE orders ADD COLUMN.. | Lock    | {116}
 130 | SELECT count(*) FROM orders;    | Lock    | {123}
```

C блокирует не A, а B: в столбце `blocked_by` стоит pid запроса ALTER. A и C друг другу не мешали бы, но между ними в очереди стоит ALTER, и каждый запрос, пришедший к таблице в эти секунды, встаёт за ним.

![Долгий SELECT в сессии A удерживает блокировку, ALTER TABLE ждёт её, а каждый новый запрос встаёт в очередь за ALTER](/sketches/alter/lock-queue.svg)

```text
B ALTER:  ждал 5.08 s, затем выполнился мгновенно
C SELECT: ждал 4.09 s
```

При реальном трафике C не один: каждую секунду в очередь попадают сотни запросов, пул соединений переполняется, и снаружи сервис выглядит полностью неработающим.

## lock_timeout

Решение: миграция не должна ждать блокировку бесконечно.

```sql
SET lock_timeout = '1s';
ALTER TABLE orders ADD COLUMN note text;
```

```text
B ALTER:  1.09 s  ERROR:  canceling statement due to lock timeout
C SELECT: 0.09 s
```

Через секунду ALTER сдаётся, и очередь сразу рассасывается. Миграция завершилась неудачей, но это несравнимо дешевле остановки сервиса: её можно повторить в более спокойный момент.

![SELECT за ALTER TABLE ждал 4.09 с без lock_timeout и 0.09 с с lock_timeout = 1s](/sketches/alter/wait-race.svg)

```bash
for attempt in 1 2 3 4 5; do
  psql -v ON_ERROR_STOP=1 -c "SET lock_timeout = '1s'; ALTER TABLE orders ADD COLUMN note text;" && break
  sleep $((attempt * 2))
done
```

## Правила для миграций

- Каждая миграция начинается с `SET lock_timeout`. В миграциях ORM то же самое: достаточно написать эту команду первой строкой SQL-файла.
- Долгие транзакции нужно найти до миграции: `SELECT pid, now() - xact_start AS age, query FROM pg_stat_activity WHERE xact_start < now() - interval '1 minute';`
- Изменения, которые переписывают таблицу, мгновенно не выполняются: это `ALTER COLUMN ... TYPE` или столбец со значением по умолчанию категории VOLATILE, например `gen_random_uuid()`. Такие изменения делают через добавление нового столбца и перенос данных порциями.
- Индекс строится через `CREATE INDEX CONCURRENTLY`: так он не блокирует запись в таблицу.
