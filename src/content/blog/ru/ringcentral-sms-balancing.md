На платформе 1000 тенантов, и каждый отправляет SMS через RingCentral. Сообщения бывают двух видов: первые и прямые сообщения (first/direct), которые не должны ждать, и bulk-кампании, уходящие тысячам получателей. RingCentral же разрешает 40 запросов в минуту на пару extension и app, а API вызывают несколько подов.

В этой задаче три независимые друг от друга проблемы:

1. **Durability.** Задача на отправку SMS не должна теряться при перезапуске Redis или пода.
2. **Scheduling.** Нужно решать, какой тенант и какое SMS идут следующими.
3. **Rate limiting.** Для одной пары extension и app все поды вместе должны укладываться в лимит 40 запросов в минуту.

Нагружать все три задачи на один лимитер очереди BullMQ не обязательно. BullMQ может остаться для запуска воркеров и фоновых задач, но порядок отправки и состояние лимита нужно вести независимо от него.

## Архитектура

```text
NestJS API             first/direct message, bulk campaign
    |
    v
PostgreSQL             sms_outbox, campaign recipients, delivery state, idempotency keys
    |                  (источник истины; transactional outbox или CDC)
    v
Kafka                  durable transport, replay, consumer groups
    |
    v
Scheduler              priority lane (first + direct) | bulk lane (справедливо по тенантам)
                       per-extension eligibility, token bucket или pacing, lease
    |
    v
RingCentral API        отдельный rate limit для каждой пары extension + app
```

Роли чётко разделены: Kafka доставляет сообщения и позволяет перечитать их заново, а PostgreSQL хранит надёжное состояние того, какие SMS ещё нужно отправить. Даже если очередь в Redis пропадёт целиком, неотправленные SMS теряться не должны.

## Rate limiter на уровне extension

RingCentral считает лимит по одному ключу:

```text
rate_limit_key = (ringcentral_account_id, extension_id, app_id, api_usage_group)
```

Согласно документации RingCentral, лимит применяется к паре «аутентифицированный пользователь и app» в разрезе группы API. Лимит по умолчанию для группы Medium составляет 40 запросов в минуту и считается по скользящему окну, а endpoint `/sms` входит в эту группу. При превышении лимита сервер отклоняет все запросы этой группы в течение 60-секундного штрафа, и каждый новый запрос запускает штраф заново.

### Почему 35, а не 40

40 в минуту это верхняя граница, а не безопасный рабочий режим. Если каждый под отправляет по 40 для одного extension независимо от других, лимит сразу нарушается. Стартовая настройка:

- Лимит RingCentral: 40 запросов/60 секунд.
- Внутренняя цель: 35 запросов/60 секунд.
- Для одного extension одновременно только 1 активный SMS POST.
- Если пришёл `Retry-After`, на это время по этому ключу новые POST не отправляются.

35 всего лишь консервативное стартовое значение, его можно менять по данным мониторинга. Если нужна строгая гарантия, необходим централизованный scheduler, соответствующий скользящему окну RingCentral.

### Где хранить состояние: Redis или PostgreSQL

| Подход | Преимущество | Риск |
| --- | --- | --- |
| Redis Lua и distributed lock | Быстро, токены выдаются атомарно | При перезапуске или failover состояние может потеряться или восстановиться устаревшим |
| Транзакция PostgreSQL и row lock | Durable, общее для всех подов | Contention и дополнительная нагрузка на базу при больших объёмах |
| Один dispatcher на ключ extension | Понятно, порядком легко управлять | При большом числе extension нужно управлять партициями и ownership |

Я выбираю хранить состояние scheduling в PostgreSQL, с lease и ownership по extension и централизованным admission control. Redis может быть лишь ускоряющим слоем, а надёжность системы не должна зависеть от состояния Redis.

```sql
CREATE TABLE sms_rate_limit_state (
  account_id      text        NOT NULL,
  extension_id    text        NOT NULL,
  app_id          text        NOT NULL,
  api_group       text        NOT NULL DEFAULT 'medium',
  next_allowed_at timestamptz NOT NULL DEFAULT now(),
  blocked_until   timestamptz,
  lease_owner     text,
  lease_until     timestamptz,
  PRIMARY KEY (account_id, extension_id, app_id, api_group)
);
```

Одной этой таблицы недостаточно. `next_allowed_at` работает только для pacing: при 35 в минуту минимальный интервал между запросами равен 60 / 35, то есть примерно 1,714 с. Для точного лимита по скользящему окну нужны ещё времена последних запросов или равноценное атомарное состояние. У каждого extension своя очередь, и остальные extension работают независимо от него.

### Параллельные поды

У нескольких подов не должно быть права одновременно отправлять запросы для одного extension. Это можно контролировать через distributed lease и fencing token:

1. Dispatcher берёт lease на extension.
2. Scheduler выбирает следующее сообщение.
3. В атомарной операции резервируется слот под запрос.
4. Выполняется HTTP POST.
5. Результат записывается в durable-состояние.

Однако в момент истечения lease старый под может всё ещё отправлять HTTP-запрос. Сам API RingCentral fencing token не проверяет, поэтому внешний POST он полностью не защищает. Lease, таймаут in-flight запроса и протокол смены ownership нужно проектировать вместе.

## Чтобы priority и bulk не мешали друг другу

Priority может обойти очередь, но не может обойти общий rate limit extension. Поэтому у каждого extension две логические очереди: `priority_queue` (first и direct сообщения) и `bulk_queue` (SMS кампаний).

```text
dispatch(extension):
    if now < blocked_until:
        return
    if request_slot_not_available:
        return

    if priority_queue has eligible message:
        message = priority_queue.pop()
    else:
        message = fair_scheduler.next_bulk_message()

    if message exists:
        reserve_rate_limit_slot()
        submit_to_ringcentral(message)
```

Priority проходит вперёд, только если HTTP POST для bulk-сообщения ещё не начался. Запрос, который уже отправляется в RingCentral, нельзя отозвать из-за того, что пришло priority-сообщение.

Внутренний бюджет extension в 35 запросов в минуту можно разделить так:

- 5 запросов/минуту в резерве для priority-сообщений.
- 30 запросов/минуту основной бюджет для bulk.
- Пока priority простаивает, свободная ёмкость отдаётся bulk, но возвращается, как только приходит priority.

Это пример, а не универсально оптимальное значение. Главное условие: bulk не должен занимать весь лимит. Если priority-трафик превышает и резерв, он тоже ждёт в рамках лимита: в пределах 40 в минуту ни один scheduler не гарантирует немедленную отправку всех priority-сообщений.

## Справедливость между тенантами: не глобальный FIFO

Если каждый из 1000 тенантов отправляет по 5000 SMS, объём bulk составляет 5 млн SMS в день. В глобальном FIFO 5000 SMS первого тенанта отодвигают всех остальных. Поэтому для bulk нужен scheduler вроде Deficit Round Robin (DRR) или Weighted Fair Queuing: в каждом раунде активные тенанты по очереди получают по одной возможности. Даже если у тенанта A ещё тысячи сообщений, B и C не ждут, пока он закончит.

Практические правила:

1. У каждого тенанта своя bulk-очередь.
2. В scheduler участвуют только активные тенанты.
3. Scheduler выбирает сообщения у тенантов по очереди.
4. Если лимит extension тенанта временно занят, scheduler переходит к следующему готовому тенанту.
5. Каждое выбранное сообщение всё равно проходит через rate limiter своего extension.

Справедливость работает на двух уровнях. На уровне тенантов большая кампания не заставляет других тенантов ждать бесконечно. На уровне extension priority и bulk делят один ключ rate limit. Если у тенантов разное число extension с разными лимитами, простой round robin не даёт тенантам равный throughput: нужна ли тенантам равная доля или extension равные шансы, это отдельное бизнес-решение.

## Чтобы bulk никогда не терялся

Persistent-настройки в BullMQ и Kafka полезны, но требование нельзя переложить только на очередь в Redis. Источник истины это PostgreSQL. При создании кампании:

1. Кампания и её получатели записываются в PostgreSQL.
2. В той же транзакции создаётся outbox-событие.
3. Outbox publisher публикует события в Kafka.
4. Consumer готовит SMS к отправке.
5. Если Redis или Kafka временно недоступны, невыполненная работа остаётся в PostgreSQL и обрабатывается позже.

```sql
CREATE TABLE sms_outbox (
  id              uuid        PRIMARY KEY,
  tenant_id       uuid        NOT NULL,
  extension_id    text        NOT NULL,
  campaign_id     uuid,
  idempotency_key text        NOT NULL UNIQUE,
  message_type    text        NOT NULL,
  payload         jsonb       NOT NULL,
  status          text        NOT NULL DEFAULT 'pending',
  attempts        integer     NOT NULL DEFAULT 0,
  next_attempt_at timestamptz NOT NULL DEFAULT now(),
  created_at      timestamptz NOT NULL DEFAULT now(),
  updated_at      timestamptz NOT NULL DEFAULT now()
);
```

Для `status` нужны как минимум такие состояния:

| Состояние | Значение |
| --- | --- |
| `pending` | Ожидает отправки |
| `claimed` | Dispatcher взял работу на себя |
| `sending` | Выполняется внешний запрос |
| `accepted` | RingCentral принял запрос |
| `retry_wait` | Ожидает времени повторной попытки |
| `unknown` | Результат запроса неизвестен |
| `failed_permanent` | Ошибка, которую повтор не исправит |

Работу, застрявшую в `claimed`, можно восстановить после истечения lease. А для работы в `sending` перед автоматической повторной отправкой нужно выяснить результат внешнего запроса. Так даже если все очереди в Redis исчезнут, `pending` и восстанавливаемая работа из PostgreSQL снова будут поставлены в очередь.

## Одно SMS не должно уйти дважды

Здесь самое жёсткое ограничение архитектуры. Idempotency key в PostgreSQL лишь предотвращает дублирование работы внутри системы, но не гарантирует, что SMS не уйдёт через RingCentral дважды:

1. Воркер отправляет POST в RingCentral.
2. RingCentral принимает SMS.
3. Ответ теряется в сети, или воркер падает.
4. В PostgreSQL сообщение не помечено как `accepted`.
5. Воркер отправляет задачу повторно, и SMS уходит второй раз.

Обычный HTTP POST не гарантирует идемпотентность во внешней системе. Есть три пути:

- **Если провайдер поддерживает idempotency key.** Для каждого логического SMS создаётся стабильный ключ, и он используется во всех повторах. На это можно опираться, только когда официально подтверждено, что endpoint поддерживает этот механизм.
- **Если результат неясен, сначала reconciliation.** Сообщение переходит в `unknown`, проверяется в message store RingCentral, и решение принимается только после того, как результат стал ясен. То, что сообщение не найдено, не всегда доказывает, что оно не было отправлено.
- **Если провайдер не даёт идемпотентности.** Нужно выбирать: при неясном результате повторять автоматически и снижать риск потери или не отправлять повторно и снижать риск дубликата.

Без идемпотентного протокола с провайдером или надёжного reconciliation две гарантии, «никогда не теряется» и «никогда не дублируется», одновременно дать нельзя. Поэтому состояние `unknown` хранится отдельно, а автоматический повтор выполняется только при ясном результате. Если дубликаты для бизнеса абсолютно недопустимы, неясный случай не отправляется повторно автоматически, а уходит на отдельную проверку.

## Обработка 429

Согласно документации RingCentral, `Retry-After` содержит число секунд до повторной попытки, а без него рекомендуется ждать не меньше 30 с. Каждый запрос, отправленный во время штрафа, запускает штраф заново.

```text
onRateLimitResponse(extensionKey, response):
    if response.status == 429:
        retryAt = now + RetryAfter(response)
        persistBlockedUntil(extensionKey, retryAt)
        releaseWorker()
        return

    if response.success:
        persistAcceptedState()
        updateRateLimitTelemetry()
```

На что обратить внимание:

- `Retry-After` может быть в секундах или в формате HTTP-date, оба варианта разбираются корректно.
- `blocked_until` хранится durable, а не в памяти пода.
- Когда для одного extension приходит 429, все dispatcher'ы по этому ключу прекращают отправлять новые POST.
- Воркер не занимается `sleep()`: следующая попытка планируется через `next_attempt_at` или delayed job.
- Заголовки обновляются в каждом ответе: когда `X-Rate-Limit-Remaining` падает до нуля, ждём по `X-Rate-Limit-Window`.
- `503`, таймауты и сетевые ошибки не то же самое, что `429`: у них другая политика повторов и неясного результата.

Ставить на 429 на паузу всю систему ошибочно. Блокируется только соответствующий ключ rate limit, остальные extension продолжают работать.

## 5 млн SMS в день: расчёт ёмкости

| Показатель | Значение |
| --- | --- |
| Bulk в день | 5 000 000 SMS |
| Средняя скорость, вся система | 57,9 SMS/с |
| Теоретический агрегат, 1000 extension × 35/мин | 35 000 SMS/мин |
| Ёмкость одного extension при 35/мин | 2100 SMS/ч |
| 5000 SMS для одного extension | 143 минуты, то есть 2 часа 23 минуты |

Расчёт исходит из 1000 независимых extension, 35 запросов в минуту на каждый и одного SMS на POST. Это теоретическая ёмкость, а не гарантированный throughput. Если все 1000 extension одновременно запустят кампании, это уже не задача scheduler, а вопрос ёмкости. Реальный результат зависит от priority-трафика, других вызовов API из группы Medium, дополнительных ограничений провайдера и того, в какое окно времени кампания должна завершиться.

Нужно учесть ещё две вещи. Во-первых, число API-запросов и число получателей SMS не одно и то же: если один POST принимает нескольких получателей, их нужно считать отдельно. Во-вторых, для массовых и автоматических сообщений (кампании, напоминания) RingCentral предлагает отдельный продукт, High Volume SMS: он позволяет отправлять до 250 000 SMS в день с одного номера и до 10 000 SMS в одном API-запросе. Через какой API пойдут кампании, меняет и лимиты, и расчёт выше.

## Этапы выхода в production

1. **Durability в PostgreSQL.** Outbox, idempotency constraint, state machine, восстановление lease и восстановление `pending`-работы.
2. **Dispatcher на уровне extension.** Общее состояние rate limit для всех подов, единственный ownership и durable-блокировка по `Retry-After`.
3. **Priority и fairness.** Высокий приоритет для first/direct, DRR для bulk и резерв для priority.
4. **Failure testing.** Перезапуск Redis, падение пода, rebalance consumer'ов Kafka, failover PostgreSQL, 429, таймауты и потерянные HTTP-ответы.
5. **Observability.** Для каждого extension: скорость запросов, оставшаяся квота, число 429, время ожидания priority, возраст bulk-бэклога, число состояний `unknown` и статистика повторов.

## Выводы

- PostgreSQL это источник истины для состояния отправки, Kafka это транспорт и replay, а Redis и BullMQ лишь быстрый слой исполнения: гарантия надёжности от них не зависит.
- Rate limit ведётся по ключу extension в durable-состоянии, общем для всех подов: 35 запросов в минуту вместо 40, один POST одновременно и блокировка по `Retry-After`.
- Priority идёт раньше bulk, но не обходит лимит. Между тенантами работает DRR, а не глобальный FIFO.
- Открытым остаётся один вопрос: пока не подтверждено, что SMS endpoint RingCentral поддерживает внешний idempotency key, гарантии «bulk никогда не теряется» и «одно SMS никогда не уходит дважды» нельзя обещать вместе.
