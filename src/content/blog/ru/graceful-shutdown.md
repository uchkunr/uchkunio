Перед удалением пода Kubernetes отправляет ему SIGTERM, по умолчанию ждёт 30 секунд и только после этого принудительно останавливает его через SIGKILL. Если в Node.js нет обработчика SIGTERM, процесс завершается сразу, как только получает сигнал, и все запросы, которые выполнялись в этот момент, обрываются.

Эксперимент: каждый запрос выполняется 2 секунды, на сервер отправляется 20 запросов, а через 0.5 секунды приходит SIGTERM.

```text
default   20 in-flight -> 20 x UND_ERR_SOCKET   /ready after SIGTERM: ECONNREFUSED
graceful  20 in-flight -> 20 x 200              /ready after SIGTERM: 503   exit: 0 after 2047 ms
```

![20 запросов по 2 секунды и SIGTERM на 0.5 секунде: сервер с поведением по умолчанию обрывает все 20, graceful-сервер завершает все 20](/sketches/shutdown/in-flight.svg)

## Четыре шага

```js
process.on("SIGTERM", () => {
  ready = false; // 1. readiness fails, the load balancer stops sending traffic
  setTimeout(() => {
    server.close(() => process.exit(0)); // 3. stop accepting, exit when in-flight requests finish
    server.closeIdleConnections();
  }, 1000); // 2. give the load balancer time to notice
  setTimeout(() => process.exit(1), 30_000).unref(); // 4. hard deadline
});
```

На первом шаге `/ready` начинает возвращать 503, и load balancer перестаёт отправлять поду новые запросы. Второй шаг нужен потому, что load balancer замечает это изменение не сразу, а только при следующей проверке readiness, и запросы, пришедшие за это время, тоже должны быть обслужены. На третьем шаге `server.close()` перестаёт принимать новые соединения и ждёт завершения уже начатых запросов. Четвёртый шаг служит гарантией: если какой-то запрос зависнет, процесс выйдет сам, не дожидаясь SIGKILL от Kubernetes.

![SIGTERM выключает readiness, через 1 секунду сервер перестаёт принимать новые соединения, завершает начатые запросы и выходит через 2 секунды](/sketches/shutdown/timeline.svg)

## Ловушка keep-alive

В первой версии сервер завершался не за 2 секунды, а за 5. После отправки ответа keep-alive соединения оставались открытыми в простое, пока не истечёт `keepAliveTimeout` (в Node.js это 5 секунд), а `server.close()` ждал их закрытия. Если во время завершения добавлять к ответу `Connection: close`, соединение закрывается сразу после ответа:

```js
if (!ready) res.setHeader("Connection", "close");
```

## Не только HTTP

Тот же порядок применим к любому ресурсу: сначала прекращается приём новой работы, затем завершается уже начатая, и в самом конце закрываются соединения. Потребители очереди перестают брать новые сообщения и доделывают те, что уже взяли, задачи cron не запускают следующий прогон, а пул соединений с базой закрывается последним. Worker в [pgmq-ts](/ru/blog/postgres-queue-in-your-transaction) при получении `AbortSignal` ведёт себя точно так же.
